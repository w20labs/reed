Reed · Design system

Reed UI — the source of truth

The locked HUD design plus the surfaces around it — badges, the menubar breadcrumb, the menu, and Settings — in one cohesive language. The dark-glass floating pill is unique to the transient HUD; the menu and Settings are standard system-appearance surfaces that share the accents, badges, glyphs, and type. Everything here describes the app as it ships today — free, open source, with dictation on the Mac.

Two accents, one rule. Charcoal (#26262A) carries the structure — selected tab, primary buttons, toggles, progress bars (mirrors SettingsStyle.charcoal). Green (#55AF48) — the logo's green, shared with the website — is the W20 spark only: the brand dot/mark, success checks, step-progress markers and the focus glow. It is a shape colour. It is never a text colour — at 12px it measures 2.76:1 on white — so the checkmarks that sit on green discs carry ink (onGreen, 6.10:1), status words like “Installed” are slate, and links are ink with an underline. Icons and glyphs count as shapes and stay green. It reads as deliberate because it is rare. Settings uses a charcoal sidebar rail on warm-greige content. The HUD and menu stay monochrome except amber/red errors. See Type below.

Onboarding — first-run flow · every step

The first-launch window is 880×640: a step-list sidebar on the left (brand + progress; done steps carry a green check, the current step a green ring with a green-tinted pill) and the step content plus a Back/Continue footer on the right. Charcoal carries structure, CTAs, and progress; Reed green is the rare spark — checks, success, the brand mark. Amber appears only as the "pending" state on required permissions. Warm-greige surfaces throughout, mirroring Onb.* in code.

Onboarding · the flow — seven steps, the same on every Mac

One flow: Welcome → Microphone → Accessibility → Hotkey → Speech model → Cleanup → You’re done (OnboardingState.Step). Every step is always listed, so the sidebar never differs between Macs, and the rail shows progress only: movement happens through Back and Continue, whose handlers own the gates. Continue waits on Microphone (granted), Accessibility (trusted) and Speech model (downloaded and loaded); Welcome, Hotkey, Cleanup and Done never block. Welcome’s Continue records the terms acceptance. Quitting mid-flow resumes on the same step. The window’s system name (Mission Control / VoiceOver — title bars are hidden) is Set up Reed.

Onboarding · Microphone — the mic row — a setting, plus one amber callout

The mic choice renders in System Settings’ own idiom: one card shared with the permission status — status row with the tint confined to the icon, hairline divider, an always-present “Dictate with” row — for every user on every Mac. When the selection is Bluetooth, the card grows a full-bleed third row: an amber callout (10% wash, clock glyph) with the consequence in bold ink and the remedy as a one-click button — Use <mic> instead, naming the best instant-start mic on this Mac — that pins it and dismisses the row. Two quieter drafts (mute footnote; ink sentence) were rejected as ignorable: the auto-advance stops the page for this line, so it must look like the reason the page stopped. (Replaced the amber advice card after founder review, 2026-08-04: it was an alarm delivering advice — five elements for one job.)

• One container: permission status and the mic row share a neutral white card — the tint lives in the status icon — plus the Bluetooth callout row, the one element that earns amber (color is state vocabulary; controls sit on neutral ground). Ungranted: the same card is the orange status row plus the grant action; denied: row two carries “Open System Settings”. The full-width tinted banner is retired on this step; other steps keep StatusBanner.
• The row IS the state — no advice arms, no Mac Studio special case, no switched-confirmation, no dangling picker. Wired users see their mic named, which is information, not noise.
• Copy is consequence-first — “Dictation will be slow to start with <name>” — because an info-tone line (“takes a moment to wake up”) didn’t read as a problem (founder review, 2026-08-04). The live device name is used as-is, no “Your” prefix: names like “Aram’s AirPods Pro” already carry a possessive.
• The callout’s button names and pins the best instant-start mic in one click, and the row dismisses itself (picking any wired mic in the menu also removes it): built-in preferred, else the first wired device — a Mac Studio has no built-in mic but may well have USB mics on the desk. Continuity iPhone mics are never recommended (a mic that can walk out of the room is bad advice). Only when nothing qualifies is the button omitted.
• Granting auto-advances only for wired/built-in; Bluetooth cancels the auto-advance so the callout gets its moment. Continue is never blocked.
• Skip rule: an already-granted mic skips the step unless the live input is Bluetooth.
• Button hierarchy: the page’s one charcoal button is the footer’s Continue. In-page actions — Grant access, Open System Settings, Use <mic> instead — are compact bordered buttons (13/500, 8-pt radius, hairline), System Settings’ own weight.

Onboarding · Done — the supervised first run, pre-warmed

“Try it — right here” is most users’ real first dictation. Two mechanisms, no new UI:

Ordering. The Bluetooth row above always precedes it (Microphone step comes before Done), so nobody reaches the try-it box without having been offered the switch.

Silent pre-warm. If the live input is still Bluetooth when the Done step appears, Reed quietly opens the mic HAL-muted first (the shipped keep-warm mechanism: the system guarantees Reed receives silence, and the orange indicator stays off — both verified on 2026-07-29) and starts the engine. The A2DP→HFP switch spends its ~1.5 s while the user is still reading the page; their press then resumes from warm at ~130 ms instead of ~1.9 s — AirPods’ first dictation feels like everyone else’s. Wired and built-in inputs deliberately do NOT pre-warm: their cold start is ~600 ms with no profile switch, and pre-warming would engage a Bluetooth output for an instant — audibly dipping the music of exactly the user who just picked a wired mic to keep their AirPods untouched. The hold persists past onboarding (existing 10-minute idle window), so the first real dictation afterwards is instant too.

Honest costs, both bounded: the ~1 s playback interruption of the profile switch moves from “when they press” to “when the page appears” (same cost, better moment — it never eats their words); and the mic is held open a little earlier than it otherwise would be, under the same system-enforced mute as every keep-warm hold. Only Bluetooth holds at all — the standing keep-warm policy. If the pre-warm fails (device vanished mid-onboarding), try-it falls back to the existing honest cold path.

Production rule · every asset on the built-in mic

The demo video and every screenshot are shot on the built-in mic, always. The claim stays about the finished writing, never the milliseconds — the video must not write a check a Bluetooth first-run can’t cash. (Recorded here on approval; it binds assets, not code.)

HUD · Bluetooth warm-up

Today every mic shows Listening from hotkey-down. On AirPods that is false for 0.5–1.5 s while macOS switches A2DP→HFP/SCO: the mic is deaf, output is muted, and the opening words do not exist. The spinner, not the waveform, is the point — a moving wave means “I can hear you”, which during the handshake is the same lie in a different form. Wired mics never enter this state.

The pop is the universal go-signal. The completion pop means one thing everywhere: the mic is live, start talking. So Bluetooth does not drop it and does not move it — it waits for it. Sequence: hotkey down → pill + spinner → mic actually live → pop → Listening + wave + timer → user speaks. Same contract as a wired mic, just later. A pop that fires before the mic can hear would make the sound mean something different on Bluetooth than everywhere else, which is worse than a delay.

No timer during warm-up — nothing is recording yet, and a running clock would imply otherwise.

Bluetooth · holding the link warm

AirPods cost ~1.9 s per press before the mic can hear. Measured on this machine over 11 presses, the wait splits cleanly and the blame is almost entirely in one place:

stagemedianwhat it is
engine.start()52 msaudio graph up
first tap frame155 mstap installed — not audible
first audible frame1855 msthe profile switch — 92% of the wait
… link already up355 mssame code, same hardware
n=11 · cold regime σ=166 ms (1657–2317) · warm regime 354/356 ms

Two presses caught the link still up and landed at 355 ms. The 1855 ms is therefore not a hardware floor — it is the A2DP→call-profile negotiation, paid again on every press because stop() tore the stream down each time. The link decays within a couple of seconds, so in normal use you are never inside the fast window.

The method: hold the stream, mute it at the system level

kAudioHardwarePropertyProcessInputMute is a HAL guarantee — “all data coming into the process for all devices will be silent”. Because macOS enforces it, macOS does not warn about it: the orange indicator stays off while muted and appears only on unmute. Verified on macOS 26.5.2 — 200 buffers at 48 kHz, peak=0.000000 throughout, no indicator; 132 ms from unmute to first audible frame.

This is the difference between discarding audio ourselves (which would deserve an indicator) and never receiving it (which does not).

launch —▸ nothing held · no indicator
   1st press —▸ 1855 ms · indicator ON
   release —▸ mute · indicator OFF · stream HELD
      next press —▸ unmute · ~132 ms · indicator ON
      release —▸ mute · indicator OFF
   10 min idle —▸ stop engine · AirPods released
the indicator is lit exactly while dictating — no more, no less

Why holding LONGER is the safer choice

Starting and stopping the stream causes a ~1 s interruption in playback — the Netflix dropout reported 2026-07-27. Holding it causes none: with the mic held open and muted, playback quality is unaffected (verified by listening, 20 s held vs 15 s released — no audible difference). So today’s two interruptions per dictation become two per session. The fix for latency and the fix for the audio glitch are the same fix, and both improve the longer the stream is held.

• Bluetooth only. Built-in and wired reach audible in ~155 ms already and gain nothing, so they never hold anything open.
• kAudioHardwarePropertySleepingIsAllowed. Audio I/O blocks idle sleep by default; holding the mic open would keep the Mac awake. This opts back out, and without it the fix would cost far more battery than the radio does.
• Released on every real boundary — device change, AirPods disconnect, quit, or 10 minutes idle. Held state is never something the user has to think about.
• The confirmation threshold drops to one buffer when already warm. Three consecutive buffers (256 ms at 4096/48 kHz) exists to filter the AirPods connect click — but a click only happens when a link is coming UP. Held open, there is nothing to filter, and the wait is self-inflicted.
• The first press of a session still pays full price. Reed holds nothing until you have shown you are dictating; the alternative is holding the link on days you never dictate at all.

Telemetry · off, never asked

Telemetry is opt-in and never asked for (DECIDED 2026-09-14, superseding the 2026-07-30 fifth-win card and P13’s onboarding checkbox): analytics and crash reports default off, and the only way on is the two Settings › Privacy toggles. There is no onboarding checkbox and no consent card.
• The defaults are the policy: a fresh install transmits nothing — pinned by TelemetryDefaultsTests, which also fails if any code outside the Settings toggles can turn telemetry on.
• First-dictation facts are local unless analytics is turned on. The transport (built-in/wired/bluetooth) and a time-to-first-audio bucket are stored in UserDefaults at the first confirmed dictation and emitted exactly once, at the first launch after the user turns analytics on. Never turned on → they never leave the Mac. The sample is therefore opted-in users only; named, not hidden.

Network · what leaves the Mac

Network · local dictation, and the few things that do use the network

Reed is local-first, not offline-only. Dictation never uses the network: audio, transcripts and cleanup stay on the Mac, and GateURLProtocol blocks every host outside a short allowlist for traffic on URLSession.shared. What does use the network:
• The speech model — downloaded once during onboarding, and again only as a repair if its files go missing (Settings › Speech model repair).
• Updates — Sparkle checks Reed’s release bucket for the appcast and update archives: automatic checks, plus Check for Updates… in the menu.
• Anonymous analytics and crash reports — only after the matching Settings › Privacy toggle is turned on (both are off by default). Analytics go to the allowlisted Aptabase host; crash reports use Sentry’s own transport, gated by its toggle.
• Links the user clicks — terms, privacy, “See exactly what we collect”, Report an issue — open in the browser.
There is no Reed account, backend, pricing check or feature-flag fetch.

Shipped behaviors — rules the app already follows, now specified

waveform meter
self-calibrating, both ends: bars are drawn relative to the session’s rolling speech reference (fast attack, ~3 dB/s decay, floored 12 dB above the rolling noise floor, attacking to 3 dB above the loudest buffer so typical speech rides mid-window and only genuine peaks hit full height) over a 25 dB window with a ^1.3 curve that spreads syllable variation across the bar range — and the silence gate is relative too: a buffer meters only if it clears the session’s rolling noise floor by 8 dB. The wave reads the same at laptop or desk distance, on hot or quiet mics, at any input gain (an absolute −42 dBFS gate read flat on quiet external-mic chains whose speech RMS sat below it). Silence still reads flat: room tone never clears its own floor’s margin. Stop talking → the wave simply stops: gated-silent buffers emit nothing, so the bars freeze exactly as they were at the last spoken syllable — no decay ramp (a decaying tail scroll-renders as a collapsing wedge), no flicker; the wave resumes on the next voiced buffer. Recording start still reads flat because the bars start flat. The pre-ASR −42 dBFS peak gate for skipping transcription is unchanged

Behavior rules. ① A missing model starts the repair on its own; outside onboarding there is no Download button. ② A press before the model lands shows the pill above and records nothing. ③ Cancel is available while bytes move, never during the compile. ④ The failure names its cause: “Not enough disk space for the speech model. Free up space and try again.”, the connection line shown above, or “The speech model couldn't be downloaded or loaded. Try again - if it keeps failing, report it from Settings → About (Report an issue).” ⑤ The notice renders nothing while idle.
